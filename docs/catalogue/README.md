# Node catalogue

One file per node type. Each says what the node means, what each provider's resolver emits for it, and why the opinions are what they are. When a resolver changes what it emits, the file changes in the same commit.

AWS, GCP and Azure each cover every node type. Where a section records a limit, it is one the provider imposes and the resolver refuses or works round rather than guesses at.

[styles.md](styles.md) is the one file that is not a node type: the colour, icon and shape each provider draws every type with, and which icon set the ids come from.

## Cost

`togen cost` estimates the monthly bill of `togen/project.json` without touching the network. AWS and Azure are priced; GCP is still arriving. Each node type's file has a Cost paragraph per provider saying which meters it is priced on and what is left out; a node type without one is listed under `not priced` in the output rather than priced at zero. On AWS the always-on types are priced on their fixed meters: a database on its instance hours and storage, a service on Fargate vCPU-hours and GB-hours for `minReplicas` tasks plus the application load balancer's hours when the resolver gives it one, a cache on its node hours, and the implicit network on the NAT gateway. On Azure they are a database on its flexible server compute (the burstable meter for small, the series' vCore meter for medium and large) and its storage, doubled for a zone redundant standby, a service on Container Apps vCPU-hours and GiB-hours for `minReplicas` replicas, and a cache on its node hours; a gateway is no resource at all (ADR 0010) and prices at zero, the virtual network is free and there is no NAT gateway, so the only implicit charge is the Service Bus Standard base unit, which a `fifo` queue brings once for the namespace all the queues share. What a node does comes from the `usage` block in `togen.yml`, keyed by node name (ADR 0009). Each node type takes a fixed set of keys, named in its Cost paragraph: a gateway `requests`; a function `invocations` and `durationMs`; a queue `messages`; a bucket `storageGb`, `egressGb` and `requests`; a service `egressGb` and `requests`; the implicit network, under the key `network`, `natGb`; a database and a cache none. The keys belong to the node type, not to the provider, so one a provider's matchers have no meter for validates and prices nothing there: a service's `requests` is a Container Apps meter on Azure and nothing on AWS, and a gateway's `requests` is an API Gateway meter on AWS and nothing on Azure, where the gateway is not a resource. `requests`, `invocations` and `messages` are rates: a number, with `k` or `M` for thousands and millions, over `/min`, `/hour`, `/day` or `/month` (`500/min`, `20k/day`, `2M/month`), normalised to a 730 hour month and rounded to a whole count. `durationMs`, `storageGb`, `egressGb` and `natGb` are plain numbers. The schema checks the shape and the rate grammar; the same check that holds `style.nodes` to the project holds `usage` to it too, so a node the project has not got, or a key the node's type does not take, fails `togen validate`, `togen cost`, `GET /api/config` and `GET /api/cost` with a dotted path such as `usage.api.invocations`. Each figure the block sets becomes a usage line at the snapshot's rate, beside the fixed ones; a figure the block leaves out stays under `not priced` by its meter's name; and a node with no entry at all is priced on defaults, which for the always-on types means its fixed lines and for the pay-per-use types (function, gateway, queue, bucket) means zero, with the line `priced on defaults, no usage set` under it either way. Several meters are tiered and the snapshot holds the first tier's rate with the point where it ends; a quantity past that point is still priced at the first tier's rate, and the line says so beneath it, in the table and in the document. Unit prices print to four places, or with as many as they need when four would show nothing, so a Lambda request reads `0.0000002` rather than `0.0000`. `togen cost --json` prints the same estimate as a document for the studio, and `GET /api/cost` serves it. The studio shows it too: a pill in the top bar carries the total and opens the same table as a panel on the right, usage lines beside the fixed ones, a tier note under a line that has one, and the footer naming the nodes priced on defaults; every card carries its subtotal (`0.00` when a pay-per-use node is on defaults, a dash when it is not priced), and the number follows each change to the project. A bad usage entry reaches the panel as the 422 the config check produces, the way a bad style entry does.

A `togen/simulation.json` feeds the same block: its traffic lands in a gateway, a service or a bucket's `requests`, a function's `invocations` or a queue's `messages`, whichever the node's `usageField` is, and a database and a cache take none, so a simulation never prices them.

Prices come from a snapshot bundled in the binary, one per provider. `internal/cost/prices/aws.json` is the AWS Price List bulk offer files trimmed to the SKUs the matchers name, and `internal/cost/prices/azure.json` the Azure Retail Prices API trimmed the same way, with the per-second and per-batch rates the API lists normalised to hours and single operations so a line reads in the unit it is quantified in. Each holds one entry per SKU per region for the regions the studio offers, the usage meters of the pay-per-use types included. `just refresh-prices` rebuilds the AWS one (about 4.5 GB of downloads, streamed, nothing kept on disk) and `just refresh-prices --provider azure` the Azure one (a few megabytes, and no credentials: the Retail Prices API is public). Either fails if any matcher matches nothing, or more than one SKU, in any region. A tiered meter, such as S3 storage or Lambda duration, is one SKU with a row per tier; the refresh keeps the first tier's rate, which is what usage is charged at until it outgrows it, and records where that tier ends as `upTo`. The snapshot records the date it was taken and the offer file versions; every estimate prints that date, and one older than 90 days adds a warning line. A weekly workflow runs `just refresh-prices --check` for each provider, which fetches and compares without writing, so a price that moved shows up as a failed check rather than a stale number. `internal/cost/testdata/*.golden` holds the table each example prints, so a price that moves is a diff to read rather than a number to trust; `go test ./internal/cost -run Golden -update` accepts it.

GCP prices come the same way, from the Cloud Billing Catalog API rather than bulk files, and `internal/cost/prices/gcp.json` is not committed yet: the API refuses unregistered callers, so the refresh needs an API key from a Google Cloud project with the Cloud Billing API enabled, read from `GCP_BILLING_API_KEY` and never from the repository.

The estimate is from on-demand list prices in USD for the project's region, over a 730 hour month, and is never a quote. Free tier, reserved instances and savings plans, support plans, tax, cross-region and internet data transfer are never included. Internet egress is the one data transfer priced, and only where the usage block gives a figure for it. Charges a matcher knows about but cannot size from the project or the usage block, such as backups beyond the allocated storage, are named in the output as not priced.
